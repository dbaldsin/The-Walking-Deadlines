# Traceability — Jassim Al-Thani (jtthani)

**Feature:** Plain-language permission explanations. Before a shell command runs, opencode's permission prompt explains what it does and why, explains its flags, links to official documentation, and treats commands on a dangerous-command list with extra care.

**Code:** [`packages/opencode/src/translator/index.ts`](../packages/opencode/src/translator/index.ts) (`shell`), with [`flags.ts`](../packages/opencode/src/translator/flags.ts), [`docs.ts`](../packages/opencode/src/translator/docs.ts) and [`danger.ts`](../packages/opencode/src/translator/danger.ts); the permission request in [`src/tool/shell.ts`](../packages/opencode/src/tool/shell.ts); [`src/permission/index.ts`](../packages/opencode/src/permission/index.ts) (`ask`, `reply`); the `dangerous_commands` setting in [`packages/core/src/v1/config/config.ts`](../packages/core/src/v1/config/config.ts). ## Requirement changes

| ID | Original (P4A) | Revised (P4B) | Why it changed |
|----|----|----|----|
| R1 | Before any command runs, the permission prompt shows a plain-English explanation of what the command does and why the current task needs it. | Before any shell command runs, the prompt shows the command, a plain-English description of what it does (or a warning when it is too complex to summarize safely), and the agent's stated reason when it gives one. The command does not run until approved; a rejected command never runs. | **Not feasible as written.** "Why the current task needs it" can only come from the agent: opencode can't check the agent's reasoning, and the agent can leave it out. Some commands (command substitution, heredocs, subshells, unmatched quotes) can't be summarized safely, and a guessed summary could hide a side effect. What C-2, C-3, O-7 and O-8 needed was to see, every time and before anything runs, what will happen and why. The revision keeps that, presents the reason as the agent's, and shows a clear warning instead of a guess. |
| R2 | The explanation covers the specific arguments: it names the package or target and explains each flag used. | The explanation names the package or target of each step. For supported commands, every flag is explained from a fixed table, combined flags (`-rf`) one by one; a flag not in the table is still listed as not explained. What a package is for comes from the agent's reason. | **Not feasible as written.** Explaining every flag of every program would need a table for thousands of programs whose flags differ by version and platform, and opencode can't know what each of the millions of npm packages is for without asking the model or the network. C-11, C-12, S-15 and O-12 wanted explanations specific to *this* command rather than a generic "npm install installs packages". The revision names the package or target, explains every flag of supported commands, and never silently skips a flag it doesn't know. |
| R3 | The default explanation is short. The user can pick "Learn more" or ask a follow-up before deciding, and the command keeps waiting. | The default explanation is at most two sentences. "Learn more" shows details without answering the prompt, so the command keeps waiting. To ask the agent a question, the user rejects with a message; the agent answers and can ask again. | **Not feasible, and can't be checked.** The prompt is raised from inside the agent's tool call, and a session runs one model turn at a time, so the agent can't answer a follow-up until that tool call ends, which needs the prompt answered first. "Short" couldn't be checked, so it is now at most two sentences. "Learn more" keeps what S-9, S-10 and S-11 asked for (no wall of text by default, details on request); asking a question works by rejecting with a message, which opencode already supports. |
| R4 | Dangerous commands are identified by a fixed, user-editable list of patterns, not by the model's judgment. | Same, and a command is dangerous when any part of it matches a listed pattern (chains, `sudo`/`env`/`time`/`nohup`, `sh -c`/`bash -c`/`eval`, subshells and `$(…)`), however its flags are ordered, combined or spelled. Commands hidden inside scripts or variables can't be identified. | **Can't be checked as written.** It didn't say what "matching a pattern" means. Taken literally, `rm -rf *` would miss `rm -fr src/`, `rm -r -f src/`, `sudo rm -rf src/` or `bash -c 'rm -rf src/'`, the same catastrophic command spelled differently, so the agent's spelling would decide instead of its judgment, which is what S-6 and O-5 objected to. The revision defines matching and states the limit. |
| R6 | Dangerous commands never offer "Allow always," so each run needs its own approval. | Same, and no earlier answer, including "Allow always" given to an ordinary command whose pattern also covers the dangerous one, lets a dangerous command run without asking. Rules the user writes in opencode.json still apply. | **Incomplete (found in Step 3).** Hiding "Allow always" from the dangerous prompt doesn't by itself give "each run needs its own approval". The R6 property showed that "Allow always" on `rm build.log` approves `rm *`, which then answered `rm -rf build/`, whether it was already waiting or ran later. The revision says no earlier answer can approve a dangerous command. It also scopes the requirement to prompts: with `bash: allow` (opencode's default) nothing is asked at all, and a rule the user writes in opencode.json is a deliberate decision, not a one-click answer. |
| R7 | Each explanation includes a link to the command's official documentation so the user can verify it. | Every supported program links to its official documentation on the project's own site (git to the subcommand's page, npm to the command's page). Unknown programs get no link rather than a guessed one, and links never come from the agent. | **Not feasible as written.** Unknown programs, project scripts (`./deploy.sh`) and made-up tools have no known official documentation, and guessing a URL could send users to a wrong or unofficial page, the kind of source S-20 and O-14 didn't trust. The revision links every program opencode knows to its own site and gives no link otherwise, so every link shown can be trusted. |
| R8 | When undoing a package install, the explanation says why the package is no longer needed and lists anything left behind. It never removes dependencies that other packages still use. | When the agent removes a package, the explanation names it, shows the agent's reason, warns about files that still import it, and lists its dependencies that stay because other packages use them. It never claims a still-used dependency will be removed. | **Partly not feasible.** "Why the package is no longer needed" can only come from the agent's reason. "Never removes dependencies that other packages still use" describes what the package manager does, not the explanation: opencode doesn't decide what `npm uninstall` removes, and npm already keeps dependencies other packages need. C-9, C-10, O-10 and S-14 wanted to know the consequences before approving (what still imports the package, what stays installed); the revision keeps that. |

R5 is kept as written: a typed confirmation can be built into every prompt. It is not implemented yet.

R1, both R4 properties, R7 and the R2 flag property passed on their first run. To check that they would catch real mistakes, I broke the code three ways: not splitting `-rf` into `-r` and `-f`, ignoring the text inside `sh -c '…'`, and linking unknown programs to a forum. Each made a property fail with a small counterexample (`rm -Rf .` not flagged, `bash -c 'git push -f origin main'` not flagged, `aaa0 --verbose` linked to Stack Overflow). The breakages were reverted. After the fixes, all seven properties pass, along with the existing tests in `test/translator`, `test/tool`, `test/permission`, `test/acp` and `test/cli/run`.

## How to run

```sh
cd packages/opencode
bun test --timeout 120000 test/explanation/explanation.property.test.ts
bun test test/translator test/tool/shell.test.ts test/permission
```

The pure properties (R2, R4, R7) run 200 cases each. R1 and R6 run 25 cases each, because every case starts real processes in its own temporary project.

CI: the `unit` job in `.github/workflows/test.yml` runs these properties through `bun turbo test` (`opencode#test` is listed in `turbo.json`). That script uses `--only-failures`, so passing tests aren't printed; the "Run explanation property tests" step runs the property file on its own so each property is listed by name.
