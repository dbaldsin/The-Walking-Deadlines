## Requirement changes

| ID | Original (P4A) | Revised (P4B) | Why it changed |
|----|----|----|----|
| R2 | The system shall automatically allow low-risk, read-only commands within a trusted workspace and require approval for destructive or sensitive operations. | A command matching an `allow` rule runs without a prompt; a command whose last matching rule is `ask`, or that matches no rule, prompts and does not run until approved; a command whose last matching rule is `deny` never runs. | **Not feasible / can't be checked.** "Low-risk", "read-only", and "trusted" can't be decided automatically for arbitrary shell commands (`cat` is harmless, `cat ~/.ssh/id_rsa` isn't), and the criteria already rely on configuration ("configured as allowed / ask"). What users needed (C-1, S-2, O-1) was for routine commands not to interrupt them and for risky ones to always reach them first. The revision makes that the user's configured rules, adds a safe default (unmatched → ask), and adds `deny`, which interviewees wanted for commands that must never run. |
| R3 | The system shall prevent execution of rejected commands and shall not automatically retry them or execute equivalent alternatives to bypass rejection. | A rejected request never runs; rejection also rejects all other waiting requests in the same session, leaves other sessions untouched, and grants nothing, so the same command asked again prompts again. A plain rejection stops the operation; a rejection with a message returns that message to the agent. | **Not feasible as stated, and the interviewees conflict.** Deciding whether two shell commands are "equivalent" is undecidable in general, so the system can't recognize every workaround. What it can guarantee is that a rejection grants nothing: any follow-up command, similar or not, goes through evaluation again and prompts unless a rule allows it. Interviewees also disagreed on what happens next: S-4 wanted the AI to stop completely, while C-3 and O-3 wanted it to explain and suggest or ask. The revision covers both: a plain reject stops the operation, and the user opts into alternatives by attaching a message. |
| R5 | The system shall support standing approval for future requests matching an explicitly approved permission pattern. | Same, **unless a configured deny rule matches the request** (deny always wins); non-matching requests are evaluated as before. | **Conflict found in Step 3** between R5 and the "deny never runs" part of R2 (and S-3, O-2: a denied command must never run). fast-check showed that approving `always` with pattern `*` for `bun install` let `ls` run although the config said `ls: deny`. The user's explicit deny is the stronger, safety-critical decision. The "always" answer was given to a prompt about a different command, and S-9 says the AI must not run something broader than what was approved. |
| R6 | The system shall evaluate changes to command targets and prevent an approval for one file from automatically authorizing different or broader file-access patterns. | Same, for every path approved "once", and for "always" approvals of paths without glob metacharacters (`*`, `?`). | **Not feasible in full (found in Step 3).** Standing approvals are stored as glob patterns, and the pattern format has no escape character. An "always" approval for a file literally named `?/a` therefore also matches `x/a`. Fixing that means changing the permission pattern format that every user config relies on. Interviewees' concern (C-6, S-7, O-6) was that approving one ordinary file shouldn't open up `.env`, `~/.ssh`, or a whole directory, and that still holds; "once" approvals still cover every path. |

R4 is kept as written: the code meets it and the property passed the first time.

## Step 3: triage log

| # | Property | Shrunk counterexample | Diagnosis | Fix |
|---|----|----|----|----|
| 1 | R5 | ruleset `[{pattern: "ls", action: "deny"}]`, approve `bun install` with always-patterns `["*"]` → `ls` became **allowed** | **Code bug and requirement conflict.** `ask` evaluated `ruleset` and `approved` as one list with last-match-wins, so a later standing approval overrode an earlier configured deny. R5 as written allowed that; R2/R3 and the interviews (S-3, O-2) forbid it. | Revised R5 (above). Code: [`src/permission/index.ts`](../packages/opencode/src/permission/index.ts): `ask` now checks the configured ruleset first, and a configured `deny` is final; standing approvals only apply otherwise. Added the regression test `reply - always approval does not override a configured deny` to `test/permission/next.test.ts` (it fails without the fix). |
| 2 | R6 | approve `?/a` with `always`, request `x/a` → **allowed** | **Requirement problem.** The code matches its glob semantics correctly; the requirement asks for something the pattern format can't express. The first generator never hit this case: it only found it after I added a "sibling" target that differs from the approved file only at `?`/`*`. | Revised R6 (above); the property now skips "always" approvals of paths containing `*`/`?` (via `fc.pre`) and still tests every path for "once". |

R2, R3 and R4 passed on their first run. After the fixes, all five properties pass (100 runs each) together with the existing 86 tests in `test/permission/`.
