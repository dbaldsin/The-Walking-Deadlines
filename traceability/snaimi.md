# Traceability: Saif Al Naimi (snaimi)

**Target feature:** Learning Recap, changed files list. When an opencode task finishes, the recap lists each file the task added, modified, deleted or renamed, and says "No files were changed during this task." when nothing changed. Source: [`learning-recap-files.ts`](../packages/opencode/src/session/learning-recap-files.ts) (`collect` and `format`), rendered by [`learning-recap-render.ts`](../packages/opencode/src/session/learning-recap-render.ts). The task diff comes from `Snapshot.diffFull` in [`snapshot/index.ts`](../packages/opencode/src/snapshot/index.ts), called from [`summary.ts`](../packages/opencode/src/session/summary.ts), which compares the snapshot taken when the task starts with the one taken when it ends. Properties: [`learning-recap-changed-files.property.test.ts`](../packages/opencode/test/session/learning-recap-changed-files.property.test.ts).

Interview evidence IDs refer to my Project 4A workbook: C = classmate (Hamad), S = course staff (Anurag, CA), O = outside interviewee.

## Requirement changes

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R6 | New. The list is grouped by status in the order added, modified, deleted, and sorted alphabetically by path inside each group, so the order in which the task made its changes never changes the output. | The list is grouped by status in the order added, modified, deleted, renamed, and sorted alphabetically by path inside each group, comparing paths character by character (a renamed file by its new path). Entries with no status come last. The order in which the task made its changes never changes the output. | **Conflict with R8, and checkability.** R8 adds renamed entries, which belong to none of the three groups, so R6 and R8 could not both hold as written. Some saved diffs also have no status, and R5 says a status is never guessed, so they need a place too. "Alphabetically" does not say how upper and lower case, `-` against `/`, or non-English names compare, so a test cannot decide whether an order is right; comparing character by character is also the order git lists files in, and git is what the interviewees check the recap against (S-30, O-35). The interviewees also disagreed on the order: Hamad and Anurag wanted added, modified, deleted (C-29, S-27), while the outside interviewee wanted removed files at the top (O-33). I kept the order two of three asked for, as in P4A. What all three needed (C-23, S-22, O-24) is unchanged: the same final changes always give the same list. |
| R7 | New. The section starts with a summary line "N files changed: A added, M modified, D deleted", and the numbers match the entries listed under it. | The section starts with a summary line "N files changed: A added, M modified, D deleted" ("1 file changed" when there is one file), followed by ", R renamed" when the task renamed files and ", U with unknown status" when some entries have no status, and the numbers match the entries listed under it. | **Conflict with R8 and R5.** After R8, a renamed file is one entry that is not added, modified or deleted, so with only A, M and D the numbers could not match the entries listed, which is the point of R7 (C-35, S-32). Entries with no status (R5 never guesses one) have the same problem. The extra counts appear only when they are not zero, so the usual line keeps exactly the format the interviewees gave (C-28, S-29, O-30) and both original acceptance examples are unchanged. |
| R8 | New. A renamed file is shown as one entry with both paths, plus its line counts if it was also edited, instead of one deleted file and one added file. | A deleted text file and an added text file are shown as one entry, "old renamed to new (renamed, +A/-D)", when at least half of the lines of the larger of the two files are unchanged between them (git's default 50% rename threshold, counted in lines). The line counts are always shown, and are +0/-0 for a file that was only moved. A move whose content can't be compared (a binary file) is still shown as one deleted file and one added file, with both paths correct. | **Feasibility and checkability.** A rename is not recorded anywhere: git only sees one file disappear and another appear, and decides whether that was a rename by comparing their content. The task diff from `Snapshot.diffFull` runs git with `--no-renames` because the same diff feeds opencode's per-file diff view, and its `FileDiff` schema only has added, modified and deleted with one path, so the recap never receives a rename. It can only infer one from the content of the deleted and added files, as git does, which needs a rule for how similar they must be; without a rule "renamed and also edited" cannot be checked. I used git's own default (at least 50% similar). Binary files have no text in the diff, so they cannot be compared; for them I used Anurag's fallback, "showing it as one deleted file and one added file is acceptable, as long as it's consistent and both paths are correct" (S-24). "Plus its line counts if it was also edited" also left the format of a plain move unclear, so the counts are always shown. The revision keeps what C-25, S-23 and O-26 asked for (one entry with both paths) and O-27's line counts for a renamed and edited file. |

I kept R1, R2, R3, R4 and R5 as written. Each is feasible with the data opencode already has: a snapshot of the project when the task starts and when it ends, compared by git, which looks at file content (R2, R3), starts from the user's working tree rather than the last commit (R4), and gives one status and one pair of line counts per file (R1, R5). None of them conflicts with another requirement, and each acceptance criterion gives a concrete task and the exact list expected.

## Test triage

**First run, before any code changes.** I ran all 11 properties against the code on `main`. Seven passed: both R1 properties, R2, R3, R4, R5 and the repository R6 property. Four failed, and all four were **code bugs**, fixed in [`learning-recap-files.ts`](../packages/opencode/src/session/learning-recap-files.ts):

- **R6** (reordering, pure). Shrunk counterexample: `docs/with space.md` (added) and `x.ts` (deleted), given in two orders. The recap listed them in whatever order it received them, so the two lists differed, and there was no grouping by status. The repository R6 property passed only because git happens to list files in path order. Fix: `format` groups entries by status (added, modified, deleted, renamed, then unknown) and sorts by path inside each group; `collect` also sorts by path.
- **R7** (summary line). Shrunk counterexample: `x.ts` deleted and `src/日本語.ts` added, each with one empty line. There was no summary line at all. Fix: `format` starts the list with `N files changed: A added, M modified, D deleted`, adding the renamed and unknown-status counts only when they are not zero. `learning-recap-render.ts` shows the summary line above the bullet list.
- **R8** (moved text file). Shrunk counterexample: `lib/z.ts` deleted and `x.ts` created with completely different content (the not-a-rename case in this property). The recap listed them in git's order, deleted before added, not in the R6 group order. The rename cases could not pass either: running only the rename case against the old code shrank to `x.ts` moved to `a-b.ts` with no edits, shown as one added and one deleted file, because the code had no rename handling at all. Fix: `format` pairs each deleted text file with the added text file that keeps the most of its lines, when at least half of the larger file is unchanged, and shows the pair as `old renamed to new (renamed, +A/-D)` with the counts between the two contents.
- **R8** (moved binary file). Shrunk counterexample: a 2-byte binary file `blob.bin` moved to `img/logo.bin`. Both paths were there, but in git's order (deleted before added), which breaks the R6 group order. Fixed by the R6 grouping; binary files are never paired as renames because their content is not in the diff.

**After the fixes**, all 11 properties pass locally on repeated runs: with the defaults (500 cases for each pure property, 20 generated tasks for each repository property), and with 50 generated tasks for each repository property (`RECAP_PROPERTY_REPO_RUNS=50`). Type checking passes, and so does every test in `test/session` and `test/snapshot` (562 passed, 0 failed; the rest are marked skip or todo in the suites themselves).

**Existing tests updated.** The R6, R7 and R8 fixes change the expected output on purpose, so six existing checks that encoded the old output were updated, not the code: three unit tests in `learning-recap-files.test.ts` (input order, no summary line), one in `learning-recap-render.test.ts` (no summary line), and two properties in `learning-recap-files.property.test.ts` from Project 3 (they compared `format`'s lines one by one, in input order, and now skip the summary line and compare the lines in any order). I also added unit tests for the R6 (all 24 orders), R7 and R8 acceptance criteria. The end-to-end recap tests in `prompt.test.ts` pass unchanged.

**Checking that R5 catches the real bug.** My first version of this feature (Project 2, PR #25) guessed the status from line counts. To confirm the R5 property would catch that, I put the line-count guess back into `collect` temporarily. The R5 property failed at once, shrinking to: an existing file `lib/z.ts` containing one empty line, and a task that removes that line. The file still exists, but the recap called it "deleted". I then removed the change again.

**CI.** The opencode package's test script runs with `--only-failures`, so passing tests don't show in the `bun turbo test` log. The `unit` job in [`test.yml`](../.github/workflows/test.yml) now has a separate step, "Run changed-files recap properties", that runs this property file from `packages/opencode` so every property is listed in the log.
